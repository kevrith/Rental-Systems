# Sub-processor list

**Last reviewed:** 2026-09-07 (Sprint 26A) · **Owner:** Kelvin · **Review cadence:** every sprint that adds or removes an integration, and at minimum quarterly

This list is generated by reading `backend/app/core/config.py` — every entry
below corresponds to a real, currently-wired integration, not an aspirational
one. An entry is added here in the same sprint the integration is added to the
codebase, which is what keeps this list honest: it is a description of what
the software does today, not a policy statement about what it is allowed to
do.

A landlord's data processing agreement (see
`data-processing-agreement-template.md` in this directory) should reference
this file by URL so a customer always sees the current list rather than a
snapshot frozen into a signed PDF.

## What "sub-processor" means here

A sub-processor is a third party that receives or could receive **personal
data** — a tenant's name, phone number, national ID, payment history, or
location — while acting on this platform's behalf. A tool that only ever
touches source code, build artefacts or infrastructure configuration (GitHub,
CI runners, a container registry) is not listed, because it never sees a
tenant's data.

## Always-on sub-processors

Used by every organisation on the platform, with no configuration required.

| Sub-processor | Purpose | Data categories | Location |
|---|---|---|---|
| **DigitalOcean** | Application hosting (droplet), managed Postgres | All customer data, at rest and in processing | Configurable region; README references a Nairobi-adjacent or EU region as the deployment target |
| **Cloudflare (R2)** | Object storage for uploaded and generated documents — lease PDFs, receipts, ID photos, meter photos | Documents containing tenant PII (national ID images, signed leases) | Cloudflare's global network; R2 buckets can be region-pinned |
| **Africa's Talking** | SMS delivery — OTP codes, rent reminders, receipts | Phone numbers, message content (which may include a tenant's name and amount owed) | Kenya |
| **Meta (WhatsApp Business Cloud API)** | WhatsApp delivery — the primary notification channel for tenants and caretakers | Phone numbers, message content | Global (Meta infrastructure) |
| **Safaricom (Daraja / M-Pesa)** | Payment collection (STK push) and disbursement (B2C payouts to owners) | Phone numbers, transaction amounts, M-Pesa receipt numbers | Kenya |
| **Paystack** | Card payment collection in the tenant portal, for tenants who do not pay by M-Pesa. Engaged only where `PAYSTACK_SECRET_KEY` is configured; with no key the card option is not shown and no data leaves the platform | Email address, transaction amounts, Paystack transaction references. Card details are entered on Paystack's own hosted page and never reach RentFlow | Nigeria/South Africa (Paystack infrastructure), serving Kenyan card rails |
| **Resend** | Transactional email — password reset, verification, statements | Email addresses, message content | US/EU (Resend's infrastructure) |
| **Browser push services** (Google FCM, Mozilla Autopush, Apple Push Notification service) | Web Push delivery for in-app notifications, routed by the browser the user chose | A push subscription endpoint (not tenant PII directly); notification title/body if the browser vendor's relay does not encrypt payload-side (Web Push payloads are encrypted end-to-end per RFC 8291, so the vendor sees ciphertext) | Vendor-dependent |

## Opt-in sub-processors

Only engaged when an organisation explicitly connects the integration. An
organisation that never opens these settings never sends data to these
parties.

| Sub-processor | Purpose | Data categories | Opt-in surface |
|---|---|---|---|
| **Anthropic** | AI lease clause analysis (US-096), meter-photo OCR (Module 5) | Lease template text (may contain tenant/landlord names if filled in); meter photo images (no PII, a dial and a wall) | Settings → Lease templates → Analyse; meter reading capture |
| **Intuit (QuickBooks)** | Accounting sync — pushes payments, maintenance costs and disbursements | Financial transaction records, no tenant PII beyond what a payment description already contains | Settings → Accounting, per organisation |
| **Xero** | Same as QuickBooks, alternative provider | Same | Settings → Accounting, per organisation |
| **BuyRentKenya** | Vacancy listing syndication | Unit photos, rent, location, contact phone for the listing | Settings → Property portals, per organisation |
| **PigiaMe** | Same as BuyRentKenya, alternative portal | Same | Settings → Property portals, per organisation |
| **Sentry** | Error tracking | Stack traces and request metadata; request bodies and credential-bearing headers are stripped before an event leaves the process (`app/core/observability.py`) — see the Security Questionnaire Answers doc, "Logging and monitoring" | Operator-side only (`SENTRY_DSN`), not a per-organisation setting — an organisation cannot opt out individually, since this is platform infrastructure, not a per-tenant integration |

## Explicitly not a sub-processor

- **ClamAV** — self-hosted virus scanning (`CLAMAV_HOST`), runs on the
  operator's own infrastructure. No data leaves the deployment.
- **Prometheus / Grafana / Jaeger** (`infra/observability/`) — self-hosted by
  default. Only becomes a sub-processor relationship if `OTEL_EXPORTER_OTLP_ENDPOINT`
  or a Prometheus remote-write target is pointed at a managed vendor, which is
  an operator decision this list would then need to reflect.

## Changing this list

Adding an integration that touches personal data means:

1. Add it to the table above in the same commit that wires it in.
2. If it is opt-in, confirm the settings page names the third party plainly —
   a customer connecting QuickBooks should see "QuickBooks" in the UI, not a
   generic "accounting provider."
3. Existing customers with an active DPA are notified of the addition per
   whatever notice period the signed DPA specifies (the template in this
   directory defaults to 30 days).
